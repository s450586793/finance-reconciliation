# 财务对账系统完整匿名化与迁移设计

## 背景与目标

当前公开仓库、产品界面、构建配置、GHCR 镜像、Compose 项目和 DSM 部署标识中包含公司品牌名称。系统尚未发布首个 `v0.2.0` 镜像版本，DSM 生产环境也尚未迁移到镜像部署，因此应在首次正式发布前完成一次性完整匿名化。

本次工作的目标是建立一条名称中性的公开发布和生产部署链路，同时保持财务原始数据、现有外部访问地址和业务功能不变。匿名化完成后，新公开资产中不得出现原公司品牌的中英文名称或其拼音形式。

已公开内容可能被第三方缓存。本方案通过删除旧公开资产来停止其继续公开，但不承诺清除无法控制的第三方缓存。

## 范围与边界

### 纳入范围

- 产品可见标题、登录页、导航和页面文案。
- README、部署说明、运维手册、设计文档及其文件名。
- 源码、测试、脚本、配置、环境变量和构建参数。
- Git 仓库名称、提交作者标识和可达历史。
- GHCR 镜像名称、构建历史和 OCI metadata。
- Compose project、容器名称以及 DSM 配置和数据目录。
- 自动升级、镜像清理、首次部署和恢复流程。

### 排除范围

- `http://sd.ace-station.top:1111` 外部访问地址保持不变。
- 发票、银行流水、微信账单、单位档案及其他财务原始数据保持真实内容。
- 无法控制的第三方缓存不属于可验证的清理范围。

匿名化不得改写业务记录，也不得改变对账关系、凭证依据或审计追溯信息。

## 统一命名

| 对象 | 新名称 |
| --- | --- |
| 产品中文名称 | 财务管理系统 |
| 产品英文名称 | Finance Reconciliation |
| GitHub 仓库 | `finance-reconciliation` |
| GHCR Web 镜像 | `finance-reconciliation-web` |
| GHCR updater 镜像 | `finance-reconciliation-updater` |
| Compose project | `finance-reconciliation` |
| DSM 配置与数据目录名 | `finance-reconciliation` |
| 环境变量及构建参数前缀 | `FINREC_` |
| 公开快照提交作者 | `Finance Reconciliation Snapshot` |

新公开源码不保留旧环境变量、旧 Compose project 或旧镜像名称的兼容别名。部署时创建只包含新变量的新配置，避免把旧标识继续带入新链路。

## 发布架构

当前私有开发分支继续作为实现来源，但不直接推送为公开历史。匿名化、测试和扫描完成后，安全快照工具从已验证提交导出允许公开的文件，并创建一个没有父提交的新根提交。

新的 `finance-reconciliation` 公开仓库只接收该中性快照及后续中性提交。其 GitHub Actions 在普通 `main` 推送时运行完整测试，在规范 `vX.Y.Z` tag 推送时发布不可变 Web 和 updater 镜像，并在两个镜像都成功后提升 Web 的 `stable` tag。

首个发布版本仍为 `v0.2.0`。在匿名化扫描和普通分支 CI 全部通过前，不创建版本 tag，不发布镜像，也不修改 DSM 生产环境。

## DSM 迁移流程

1. 匿名验证两个 `v0.2.0` 镜像可拉取，并核对版本、revision 和创建时间 metadata。
2. 在旧服务之外创建独立备份，覆盖 PostgreSQL、上传文件、导出文件、配置和恢复所需信息。
3. 验证备份存在、非空且可读取，再停止旧 Compose 服务。生产环境始终只允许一个 PostgreSQL 实例使用目标数据。
4. 将配置和数据迁移到名称中性的 DSM 目录。同一存储卷优先使用可回滚的原子目录切换；跨卷时先复制、校验，再切换引用。
5. 使用 Compose project `finance-reconciliation` 启动 `db`、`web` 和 `updater`，执行数据库迁移并等待健康检查。
6. 保持现有外部端口转发不变，使 `http://sd.ace-station.top:1111` 指向新的 Web 服务。
7. 验证登录、导入中心、发票台账、对账工作台、报表、升级页和健康检查。
8. 核对数据库关键表记录数和上传文件清单，确认业务数据未被匿名化流程改写。
9. DSM smoke 全部通过后清理旧容器和不再需要的旧镜像；在此之前保留完整回滚资产。

任一步骤失败都必须停止后续清理。若新服务已经启动，则停止新 Compose project，恢复旧目录引用和旧 Compose 服务，并使用独立备份处理数据恢复。失败处理不得同时启动新旧两个数据库实例。

## 自动升级与镜像清理

Web 端升级继续采用现有的受控 updater 架构。升级器只接受符合规范、版本高于当前版本且 metadata 完整的目标镜像。

升级成功后，系统在数据库迁移、Web 健康检查和版本确认都通过时自动清理不再使用的旧 Web 镜像。当前运行镜像、当前 updater 镜像以及完成回滚所需的镜像不得提前删除。升级失败或清理状态不确定时，系统保留相关镜像并返回可操作的固定错误状态。

updater 自身继续使用不可变 tag 手动换版，不通过 Web 请求替换正在执行升级事务的 updater 容器。

## 旧公开资产处理

新的公开仓库、GHCR 镜像和 DSM 生产环境全部验证成功后，按以下顺序处理旧资产：

1. 再次确认新仓库可匿名 clone、新镜像可匿名 pull、DSM 生产服务健康。
2. 删除旧 GHCR Web 和 updater 包。
3. 删除旧公开 GitHub 仓库。
4. 检查旧公开 URL 不再直接提供仓库或包内容。

旧资产删除是最终步骤，不得为了提前隐藏名称而牺牲迁移回滚能力。

## 安全与错误处理

- 所有部署与扫描工具默认 fail-closed，缺少输入、校验异常或状态不明确时终止操作。
- 日志仅输出固定错误类别和非敏感状态，不回显 Token、密码、Cookie、`.env` 内容或业务数据。
- 生产凭据只保存在 DSM 配置中，不进入 Git、构建上下文、镜像层、OCI metadata 或测试产物。
- GitHub 发布只使用标准 `GITHUB_TOKEN` 的最小 package 权限。
- 删除仓库、包、容器、镜像或目录前必须重新确认其不属于当前运行或回滚链路。

## 测试与验收

### 代码质量门

- Python 全量测试和覆盖率门槛通过。
- Ruff 通过。
- JavaScript 单元测试通过。
- Playwright 端到端测试通过。
- Compose、DSM smoke、公开快照和 release contract 测试通过。
- 所有因环境变量、镜像、Compose project 和路径改名而变化的公共行为均有正常、边界和失败测试。

当前验证基线为 Python `1005` 项、JavaScript `31` 项、Playwright `10` 项和 `83.90%` Python 覆盖率。匿名化后的结果不得低于该功能基线，覆盖率不得低于项目既有门槛。

### 匿名化门

扫描必须大小写不敏感，并检查：

- 新公开仓库的文件名与文件内容。
- 新公开仓库全部可达 Git 提交、tree 和 blob。
- Web 与 updater 镜像文件系统、构建历史和 OCI labels。
- GitHub 仓库名称、描述、Actions 工作流显示内容和 GHCR 包名称。

上述公开范围内，原公司品牌的中文名称、英文拼音和大小写变体命中数必须为 `0`。真实财务数据不进入公开扫描输入，也不作为匿名化测试夹具发布。

### DSM 验收门

- `http://sd.ace-station.top:1111` 可访问且 Owner 可登录。
- 导入、发票、流水、单位、对账、报表和升级页面可正常读取。
- 数据库关键表记录数与迁移前一致，上传文件清单无缺失。
- 当前 Web 和 updater 版本均为 `v0.2.0`，健康检查通过。
- 一次受控 Web 升级演练成功，旧镜像仅在成功门满足后被自动清理。
- 一次失败或恢复路径演练证明不会删除回滚资产。

只有代码质量门、匿名化门和 DSM 验收门全部通过，才可删除旧公开资产并宣布迁移完成。
